지금까지
아키텍처는 매번 달라도 고민은 매번 같습니다.
왜 우리가 갖고 있어야 하나

이 미션이 계속되는 한, 자산은 IaC입니다

우리 팀 미션 중 하나가 여러 프로젝트의 클라우드 구조를 설계하는 일입니다. 그 판단이 코드와 문서로 남지 않으면 팀의 역량이 개인의 경험으로만 쌓입니다.

고민이 남지 않으면 판단의 품질이 매번 사람에 따라 달라집니다. 자산화의 목적은 일관성입니다.

코드·결정·규약, 세 가지를 남깁니다

첫째

코드

소싱은 태그로 고정합니다. 오늘 가져온 코드와 내일 가져온 코드가 달라지면 안 됩니다.

둘째

결정

반복되는 설계 판단과 합의도 문서로 만들어 자산에 넣습니다.

  • output 공유 대신 Name 태그로 조회합니다. 워크스페이스를 쪼개도 값이 오갑니다
  • Security Group rule은 개별 리소스로 분리합니다. inline으로 몰면 순환 의존성과 전체 교체가 생깁니다
  • 계정 간 순환 의존성은 Terraform 밖으로 뺍니다. TGW RAM 공유 수락을 CI 단계로 옮겼습니다
  • 리소스를 추가할 때 네이밍 컨벤션과 약어 카탈로그도 함께 정의
셋째

규약

  • tofu만 씁니다. terraform과 섞으면 lock 파일이 꼬입니다
  • .tf를 쓰기 전에 설계 문서 승인부터
  • 릴리스 태그는 바꾸지 않습니다. 참조 중인 버전이 몰래 바뀌는 사고를 막습니다
  • 컴포넌트별 semver, 전 모듈 0.y.z. 모듈마다 성숙 속도가 다릅니다
  • 사람이 만들든 Claude Code에 위임하든 규약은 동일

규칙이 문서로 있어야 사람도 AI도 같은 기준으로 판단합니다.

Part 2 · 아키텍처 패턴

addon을 클러스터마다 따로 관리하게 됩니다

클러스터 하나면 그 자리에서 설치합니다. 둘 이상이면 정책 하나 추가하는 일이 클러스터 수만큼의 반복이 됩니다.

addon: 클러스터에 공통으로 설치하는 운영 컴포넌트(정책 엔진, 오토스케일러, 인그레스 컨트롤러 등).

증상
  • 버전을 하나 올리려면 클러스터 수만큼 같은 작업을 반복
  • dev → stg → prod 순차 검증은 정상. 그런데 그 차이가 의도인지 사고인지 가릴 지점이 없음
  • 전 클러스터가 같아야 할 Kyverno(정책 엔진)까지 제각각이 되고, 장애가 나야 알게 됨
클러스터 4 × addon 5 = 관리 포인트 20

관리 포인트도 늘어납니다. 클러스터를 하나 늘릴 때마다 관리할 곳이 addon 수만큼 함께 늘어납니다.

Part 2 · 아키텍처 패턴

hub에 모으고, spoke는 등록만

ArgoCD는 hub 한 곳에만 직접 운영(self-managed)하고, spoke 클러스터는 원격으로 등록만 합니다.

허브-스포크 등록과 팬아웃
달라지는 것

Kyverno 버전 올리기 = 커밋 한 번

platform-gitops에 Kyverno 버전을 커밋하면 대상 클러스터가 자동으로 맞춰집니다. 클러스터가 늘어도 addon 정의 파일은 늘지 않습니다.

용어

ArgoCD: Git 저장소의 상태를 클러스터에 계속 맞춰주는 GitOps 도구. 클러스터 안에서 스스로 Git을 당겨옵니다(pull).

spoke 등록: hub의 ArgoCD가 다른 클러스터의 API 서버에 접속할 수 있도록 자격증명을 등록하는 것.

이제 클러스터를 하나 늘려도 관리할 곳은 늘지 않습니다. spoke마다 반복하던 일이 커밋 한 번으로 끝납니다.

Part 2 · 아키텍처 패턴

addon마다 내보내는 방식을 고릅니다

selector 하나가 누가 받고 어떤 버전을 받는지를 정합니다. 세 가지를 씁니다.

uniform · 전 클러스터

같은 버전을 모두에게

라벨의 존재 여부만 봅니다. 클러스터를 하나 등록하는 행위 자체가 곧 배포가 됩니다.

# gateway.yaml generators: - clusters: selector: matchExpressions: - key: environment operator: Exists

우리가 소유한 CR·정책이 여기입니다. 버전이 main 하나라 나눌 것이 없습니다.

staged · 티어별 승격

비운영에서 먼저, 검증 후 운영

tier 라벨로 ApplicationSet을 나누고 각각에 버전을 답니다.

# karpenter.yaml generators: - clusters: selector: matchLabels: {tier: nonprd} targetRevision: 1.15.0 --- selector: matchLabels: {tier: prd} targetRevision: 1.14.0

깨지면 클러스터가 망가지는 것이 여기입니다. Karpenter, ALB Controller, Gateway API CRD, 그리고 Kyverno 엔진(웹훅이 죽으면 모든 배포가 막힙니다).

opt-in · 라벨 구독

라벨을 단 클러스터에만

cluster Secret에 붙인 라벨 값을 matchLabels로 지정해 대상을 고릅니다.

# keda.yaml generators: - clusters: selector: matchLabels: addon-keda: enabled

AWS에서 KEDA가 이 경로를 탑니다. Azure는 KEDA가 완전 관리형이라 이 경로 자체가 필요 없습니다. Part 3에서 다시 나올 차이입니다.

어느 클러스터가 어떤 버전을 쓰는지 저장소만 보면 알 수 있습니다.

Part 2 · 아키텍처 패턴

hub 하나에 모았으니, 가드레일이 필요합니다

배포 편의를 얻은 만큼 한 번의 실수가 닿는 범위도 커졌습니다. 두 가지로 막습니다.

self-heal · prune

Git과 다르면 되돌립니다

클러스터에서 직접 고친 값은 다음 sync에서 되돌아갑니다. 전 addon이 같은 설정을 씁니다.

syncPolicy: automated: prune: true # Git에서 지운 건 클러스터에서도 selfHeal: true # 손댄 변경은 되돌림

장애 대응으로 급히 손을 댔더라도 Git을 고쳐야 반영됩니다.

AppProject

저장소 쪽 실수를 막는 층은 여기뿐입니다

argo-cd 차트 기본값이 application controller에 cluster-admin을 줍니다. RBAC으로는 막을 게 없습니다.

  • sourceRepos 어느 차트 저장소에서 받는가
  • destinations 어느 클러스터·네임스페이스에 배포하는가
  • clusterResourceWhitelist 어떤 cluster-scoped kind를 만드는가

기본 차단에서 시작해 addon마다 필요한 kind만 엽니다.

클러스터 쪽 손댐은 self-heal이, 저장소 쪽 실수는 AppProject가 막습니다.

Part 3 · ① 그대로 옮겨졌다

상위 스코프를 쓸 수 있어도, 권한은 클러스터마다 줬습니다

hub ArgoCD가 spoke 클러스터에 접근하는 권한입니다. Azure RBAC은 구독·관리 그룹 스코프로 한 번에 줄 수 있지만, aks-reference-infra는 spoke 클러스터마다 줍니다.

두 클라우드에서 같은 원칙
  • 모듈 인터페이스 · Name 태그 조회 · 태그 고정 소싱
  • 3계층 소유 · 허브-스포크 GitOps
  • hub는 전부 private
  • 권한은 리소스를 소유한 쪽이 부여 ← 이 장
클러스터 스코프로 제한한 이유
  • Azure 랜딩존은 hub와 spoke를 다른 관리 그룹에 배치합니다. hub는 네트워크 연결 전용 구독에, spoke는 워크로드 구독에 들어갑니다. 구독 스코프로는 둘을 함께 못 덮고, 상위 관리 그룹까지 올라가야 합니다
  • 그런데 Microsoft는 관리 그룹 스코프 RBAC 할당을 권고하지 않습니다. 권한이 과도해지고 하위 구독까지 상속되기 때문입니다. 플랫폼 팀이 필요할 때만 권한을 켜는 예외는 있지만, ArgoCD는 워크로드 ID(관리 ID)로 인증하므로 권한을 항상 열어둬야 합니다

Part 3 · ② 방법을 바꿨다 · Pod IP 대역

IP를 아끼는 목표는 두고, 대역을 쓰는 방법을 바꿨습니다

IP가 부족한 엔터프라이즈 환경을 전제로 AWS에서 비라우팅 대역 재사용을 설계했습니다. 같은 방법을 Azure로 옮기자 두 곳에서 막혔습니다.

AWS · custom networking

100.64.0.0/16을 모든 VPC가 재사용

Pod는 VPC secondary CIDR에 만든 Pod 전용 서브넷에서 IP를 받고, VPC 밖으로 나갈 때 노드 IP로 SNAT됩니다.

spoke가 늘어도 Pod 대역을 조율할 필요가 없습니다.

Azure · pod_subnet · 0.1.0 기본

같은 방법을 옮겼더니

  • 대역이 겹치면 라우팅이 깨집니다. hub 100.64, dev 100.65로 따로 줘야 했고, 대역을 재사용할 수 없었습니다
  • AKS가 관리하는 Karpenter인 NAP(Node Auto Provisioning)이 이 모드를 지원하지 않습니다. 메인테이너가 공식 이슈에서 명시했습니다
Azure · overlay · 0.3.0부터 기본

Pod IP를 VNet 밖으로 뺐습니다

노드 밖 트래픽은 노드 IP로 SNAT됩니다. hub와 spoke가 같은 Pod 대역을 다시 쓰고, NAP도 동작합니다. Microsoft도 Overlay를 기본으로 권고합니다.

트레이드오프: NSG 플로우 로그의 Pod 단위 가시성 상실. AKS 유료 기능인 Advanced Container Networking Services로 일부 보완합니다.

Overlay로 hub와 spoke가 같은 Pod 대역을 쓰니 IP를 아끼는 목표는 그대로 지켰습니다. 기본값을 바꾼 근거는 azure/network.md에 남겼습니다.

Part 4 · 지금 옮기는 이유

ingress-nginx 지원이 끝났습니다(EOL)

기존 배포는 계속 동작하지만, 지원 종료 이후 새 취약점의 패치는 나오지 않습니다.

일정

Kubernetes SIG Network · Security Response Committee가 지원 종료 발표
2026-03
업스트림 지원 종료. 릴리스·버그 수정·보안 패치 중단
2026-11
AKS 관리형 NGINX(App Routing) 지원 종료. 보안 패치 중단
Azure

관리형 NGINX가 그 위에 있습니다

App Routing add-on은 ingress-nginx 기반이라 2026-11까지 옮겨야 합니다. Microsoft는 App Routing의 Gateway API 구현을 후속으로 권고하고, AKS Automatic 1.36 이상 신규 클러스터에서는 기본값으로 켰습니다.

AWS

ALB Controller는 Ingress를 그대로 써도 됩니다

ingress-nginx 위에서 돌지 않고, Ingress API도 제거 계획이 없습니다. 다만 Kubernetes는 Ingress를 frozen으로 두고 Gateway API를 권장하며, ALB Controller도 2026-03에 Gateway API를 GA로 지원합니다. ingress-nginx를 자체 설치한 클러스터는 Azure와 같은 일정입니다.

Azure는 옮겨야 하고, AWS는 안 옮겨도 됩니다. 그래도 두 클라우드 모두 Ingress를 Gateway API로 바꿉니다.

Part 4 · 앱팀이 쓰는 것

앱팀이 쓰는 HTTPRoute는 두 클라우드에서 같은 파일입니다

구현체 차이는 Gateway 쪽(gatewayClassName과 internal LB 설정)에만 있고, 그 파일은 플랫폼팀 저장소에 있습니다.

앱팀 저장소 · EKS와 AKS 공통
apiVersion: gateway.networking.k8s.io/v1 kind: HTTPRoute metadata: name: orders namespace: orders spec: parentRefs: - name: shared-gateway namespace: gateway-system rules: - matches: - path: type: PathPrefix value: /orders backendRefs: - name: orders port: 8080
플랫폼팀 저장소 · EKS Gateway
metadata: name: shared-gateway # 양쪽 같음 namespace: gateway-system spec: gatewayClassName: alb # ← 다름 infrastructure: parametersRef: # ← 다름: 내부 LB kind: LoadBalancerConfiguration
플랫폼팀 저장소 · AKS Gateway
metadata: name: shared-gateway # 양쪽 같음 namespace: gateway-system spec: gatewayClassName: approuting-istio # ← 다름 infrastructure: annotations: # ← 다름: 내부 LB service.beta.kubernetes.io/azure-load-balancer-internal: "true"

Ingress에서는 annotation 때문에 구현체마다 매니페스트가 달랐습니다. Gateway API로 옮기면 앱 저장소의 라우팅 파일이 클라우드와 무관해집니다.
