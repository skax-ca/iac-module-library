## 0. 배경 — 왜 지금 뒤집는가

이 repo는 첫 모듈부터 `vpc-v1.0.0`으로 시작했고, 2026-08-05 기준 4개 태그를 발행했다.
**1.x를 택한 명시적 결정은 없었다** — 기본값처럼 쓰였다.

그 대가가 실측으로 두 번 나타났다.

| # | 사건 | 무엇을 드러냈나 |
|---|------|----------------|
| 1 | **`eks-cluster-v1.0.0` 태그를 `74bbf51`로 이동**(2026-08-04) | semver 원문은 *"Once a versioned package has been released, the contents of that version MUST NOT be modified"* 라고 못박는다. CLAUDE.md가 *"소비자 0일 때만"* 이라는 예외로 정당화했지만, **예외를 발명해야 했다는 사실 자체**가 1.0.0이 이른 약속이었다는 신호다. `0.x`였다면 `0.2.0`을 내면 끝이었다 |
| 2 | **D-EXTDNS-ZONE의 마이너/메이저 판정 논쟁**([`design/20 §5.1-8`](../design/20-eks-module.md)) | 교차변수 validation 하나를 두고 *"plan을 거부하게 되니 계약 변경인가"* 를 문단으로 논증해야 했다. `0.x`에서는 **판정 자체가 존재하지 않는다** |

🔑 **두 사건은 같은 뿌리다** — *"안정 계약"이라는 약속을 지킬 준비가 안 된 상태에서 `1.x`로
이미 그 약속을 해버렸다.* 증상을 하나씩 누르는 대신 뿌리를 고친다.

**현재 소비자 현황**: 외부 고객사 **0**. 유일한 소비자는 우리 자신의 레퍼런스 repo
`iac-reference-infra`(`live/dev/networking`·`live/dev/eks`)다. 되돌리는 비용이 앞으로 계속
낼 비용보다 싼 **마지막 시점**이다.

## 1. 결정 요약

| ID | 결정 | 근거 |
|----|------|------|
| **D-VER-ZERO** | 계약이 굳기 전의 모듈은 **`0.y.z`** 를 쓴다. 이 구간에서는 **파괴적 변경도 마이너로 흡수**하고, 소비자에게 안정성을 약속하지 않는다 | [semver.org](https://semver.org/): *"Major version zero (0.y.z) is for initial development. **Anything MAY change at any time.** The public API SHOULD NOT be considered stable."* — 지금 이 repo의 실제 상태를 정확히 서술하는 유일한 번호 체계다. 위 §0의 두 사건이 전부 이 구간에서 소멸한다 |
| **D-VER-RESET** | 기존 `1.x` 태그 4개를 **같은 커밋에 `0.x`로 재매핑**하고 `1.x`는 삭제한다 | 이력을 버리지 않으면서 번호 체계를 정정하는 유일한 방법. 안전성은 §3.1에서 실측으로 확인했다 |
| **D-VER-NEW** | **신규 모듈은 `0.1.0`에서 시작**한다. `1.0.0`으로 시작하지 않는다 | [Cloud Posse](https://docs.cloudposse.com/best-practices/developer/semver/)(대규모 Terraform 모듈 라이브러리 운영사)의 실제 방침과 동일: *"We always start projects off at `0.1.0`."* 다음 적용 대상은 `bastion`([`design/40`](../design/40-bastion.md)) |
| **D-VER-ONE** | `1.0.0`은 **모듈별 계약 안정 선언**으로 컷한다. 판정 기준은 §2의 체크리스트이며, **전 모듈 일괄 컷을 하지 않는다** | 컴포넌트별 semver([`01 §2.1`](01-module-strategy.md))의 귀결. `vpc`(얇은 스크래치)와 `eks-cluster`(upstream 21.x facade)는 churn 속도가 근본적으로 다르다 — 묶으면 vpc가 한 줄도 안 바뀌었는데 eks 때문에 번호가 오르고, 소비자는 매번 "vpc는 뭐가 바뀌었지"를 확인해야 한다(monorepo lockstep versioning의 고전적 실패) |

> ⛔ **버전 혼재(`vpc-v0.3.0` + `bastion-v0.1.0` + 훗날 `vpc-v1.0.0`)는 결함이 아니라 정보다.**
> 어느 모듈의 계약이 굳었고 어느 것이 아직인지를 **번호가 스스로 말한다.** Cloud Posse가
> 모듈 fleet 전체에서 실제로 이렇게 운영한다. "보기 안 좋으니 맞추자"는 제안이 나오면
> D-VER-ONE의 근거를 먼저 읽는다.

### 1.1 이 결정이 인정하는 비용 (반론을 기록한다)

**가장 강한 반론은 semver 자신이 준다.** FAQ: *"If your software is being used in production,
it should probably already be 1.0.0."* — `eks-cluster-v1.0.0`은 실제 AWS 계정에 apply되어
클러스터가 돌고 있고 과금 중이다([`design/20 §4.1`](../design/20-eks-module.md)).
**semver의 문자만 보면 `1.0.0`은 조기 발행이 아니었다.**

그럼에도 `0.x`를 택하는 이유:

- 그 "production"은 **우리 자신의 레퍼런스 dev 환경**이지 고객사 프로덕션이 아니다.
  이 repo의 산출물이 향하는 곳은 고객사이고, 그 계약은 아직 한 번도 인도되지 않았다.
- semver가 `1.0.0`의 실질 요건으로 드는 것은 사용처가 아니라 **"backward compatibility를
  많이 걱정하고 있는가"** 다. 우리는 정반대다 — §0의 두 사건이 *"아직 자유롭게 바꿔야 한다"* 를
  증명했다.

⚠️ **버전 번호가 뒤로 간다**(`v1.2.0` → `v0.3.0`)는 것은 실제 비용이며, 사람의 혼동으로
나타난다. 도구는 영향받지 않는다(§3.1). 이 비용은 **한 번만** 지불되고, 대안은 같은 비용을
릴리스마다 무한히 지불하는 것이다.

## 2. `1.0.0` 컷 기준 — 모듈별 계약 안정 선언

> 🔑 **기준을 문서에 박는 것이 이 절의 목적이다.** 기준이 없으면 "이제 1.0.0인가"가
> 릴리스마다 재논쟁된다 — §0이 기록한 실패가 정확히 그것이었다.

한 모듈이 아래 **5개를 전부 만족할 때** `1.0.0`을 컷한다. 하나라도 미달이면 `0.y.z`를 유지한다.

| # | 기준 | 판정 근거 (문서 실물) |
|---|------|----------------------|
| 1 | **인터페이스 변경 사유가 소진됐다** — 그 모듈의 열린 항목 중 **변수·출력 이름을 바꾸는 것이 없다** | 해당 설계 문서의 「열린 항목」 절. *수요 발생 시 착수* 성격의 기능 추가는 무방하다(마이너로 흡수 가능) |
| 2 | **apply 판정표에 `❌`와 `⏸`가 없다** | [`design/20 §4.1`](../design/20-eks-module.md) 형식의 판정표. `tofu test` 통과는 이 기준을 대체하지 못한다 — mock provider가 판정할 수 없는 항목이 존재한다(D-EXTDNS-ZONE이 실증) |
| 3 | **실제 소비 루트가 `apply`까지 성공**했고, 그 형상이 판정표에 기록됐다 | 소비 repo의 배포 사실([`design/50` D26](../design/50-reference-consumer-repo.md)) |
| 4 | **`02 §4` 공통 검증 게이트 전항 통과** + 설계 문서 상태가 `✅` | [`docs/README.md`](../README.md) 상태표 |
| 5 | **예제·`tests`·릴리스 기록이 갖춰졌다** | `examples/<module>-*/` · `modules/<module>/tests/` · 설계 문서의 릴리스 기록 절 |

**`1.0.0` 이후에 달라지는 것**: 계약 파괴가 **마이너로 흡수되지 않고 메이저를 요구**한다
([`01 §2.3-5`](01-module-strategy.md)의 semver 거버넌스 계약이 이 시점부터 실효를 갖는다).
그래서 `1.0.0`은 축하가 아니라 **자유의 포기**다 — 준비되기 전에 컷하지 않는다.

### 3.1 안전성 — 실측으로 확인함 (2026-08-05)

| 확인 항목 | 실측 결과 | 함의 |

| `vpc-v1.2.0..HEAD -- modules/vpc` | **변경 없음** | 재매핑 태그가 가리키는 모듈 소스가 현행과 동일 |
| `eks-cluster-v1.0.0..HEAD -- modules/eks-cluster` | **변경 없음** | 〃 |
| git 소싱의 버전 해석 | `?ref=<tag>`는 **정확 ref 체크아웃** — `~>` 같은 제약을 해석하지 않는다([`02 §3`](02-naming-tagging-and-pinning.md)) | **번호가 뒤로 가도 파이프라인이 깨지지 않는다.** registry 기반 생태계였다면 불가능했을 조치다 |

→ 재매핑 태그는 구 태그와 **동일한 커밋**을 가리키므로, 소비 repo가 재핀해도 OpenTofu가
내려받는 모듈 소스는 **바이트 동일**하다. **라이브 EKS 클러스터에 무영향이어야 한다.**
⚠️ 단 이것은 **plan으로 실측할 항목**이지 가정할 항목이 아니다(§3.2 순서 2).

### 3.2 순서 — 되돌릴 수 있는 상태를 유지한다

🔑 **구 태그 삭제는 맨 마지막이다.** 순서를 바꾸면 롤백 경로가 사라진다.

| 매핑 | 커밋 |
|------|------|
| `vpc-v1.0.0` → **`vpc-v0.1.0`** | `27cd26e` |
| `vpc-v1.1.0` → **`vpc-v0.2.0`** | `4b9bacd` |
| `vpc-v1.2.0` → **`vpc-v0.3.0`** (현행) | `069a87b` |
| `eks-cluster-v1.0.0` → **`eks-cluster-v0.1.0`** (현행) | `74bbf51` |

1. **새 `0.x` 태그 4개 생성 + push.** 이 시점에 두 체계가 공존한다(의도된 과도기).
2. **소비 repo 재핀 + `plan` 실측** — `live/dev/networking`(→ `vpc-v0.3.0`),
   `live/dev/eks`(→ `eks-cluster-v0.1.0`). **`No changes` 를 확인한다.**
   ⚠️ 여기서 diff가 나오면 **즉시 중단하고 원인을 찾는다** — 구 태그가 아직 살아 있으므로 되돌릴 수 있다.
3. **문서 갱신**(§3.3) — 이 repo + 소비 repo.
4. **구 `1.x` 태그 삭제** — 로컬(`git tag -d`) **및 원격**(`git push --delete origin`). 원격에 4개 다 있다.


### 3.5 D-EXTDNS-ZONE에 미치는 영향

[`design/20 §5.1-8`](../design/20-eks-module.md)의 다음 릴리스는 **`eks-cluster-v1.1.0`이 아니라
`eks-cluster-v0.2.0`** 이 된다.

⭐ **이 전환의 첫 실익이 여기서 바로 나온다** — §5.1-8이 마이너/메이저 판정에 쓴 논증 문단이
**불필요해진다.** `0.x`에서는 계약 파괴 여부와 무관하게 마이너다.
해당 절의 semver 판정 서술을 **이 문서 참조로 교체**한다(논증을 지우는 것이 아니라, 판정이
필요 없어졌음을 기록한다).

## 4. 기각안

| 안 | 기각 근거 |
|----|-----------|
| **현행 `1.x` 유지** | §0의 두 비용을 릴리스마다 계속 지불한다. 되돌리는 비용은 지금이 가장 싸다(외부 소비자 0) |
| **개발 완료까지 태그를 안 달고 GA에 `1.0.0` 일괄 발행** | ⛔ **소비 경로가 태그 하나뿐이다**([`02 §3`](02-naming-tagging-and-pinning.md)). 태그를 안 달면 소비 repo가 `ref=main`을 써야 하고, 움직이는 참조는 *"어제 통과한 plan이 오늘 다르다"* 를 만든다. 실제로 D13(SubnetGroup 태그)이 소비 repo에 전달된 유일한 통로가 태그였다. 게다가 일괄 발행은 D-VER-ONE의 근거(컴포넌트별 cadence 분리)를 정면으로 깬다 |
| **GA 시점에 `v2.0.0` 일괄 컷** | 계약이 바뀌지 않았는데 메이저를 올리는 것은 semver 오용이다. 메이저는 "고객사 인도"가 아니라 "계약 파괴"를 뜻한다 |
| **`1.x` 태그를 남긴 채 `0.x` 병행** | `git tag -l`에 두 체계가 영구히 섞인다. 재매핑이 이력을 보존하므로 남길 이유가 없다 |
| **과거 태그를 지우고 현 시점부터 `0.1.0` 새로 시작** | 릴리스 3회의 이력이 태그에서 사라진다. `design/10 §3`의 게이트 실측 기록이 **가리킬 태그가 없는 기록**이 된다 |

## 5. 열린 항목

1. **라이브러리 레벨 GA 신호가 여전히 없다.** D-VER-ONE은 모듈별 판정만 정의한다 —
   *"이 태그 조합을 고객사에 인도해도 되는가"* 에 답하는 산출물(번들 매니페스트/릴리스 노트)은
   미정이며, **`01 §7-2`는 이 부분만 열린 채로 남는다.**
   검토 시점: 첫 고객사 인도 준비 단계. semver로는 답할 수 없는 축이라 별도 형식이 필요하다.
2. **CHANGELOG 형식** — `01 §7-2`의 나머지 절반. 현재는 태그 메시지 + 설계 문서 릴리스 기록이
   그 역할을 나눠 갖고 있다. 모듈 수가 늘면 재검토한다.
3. **`1.0.0` 컷의 최초 후보**는 `vpc`다(§2 기준 5개 중 1·2·3·4·5를 대체로 충족하나,
   [`design/10`](../design/10-vpc-module.md) 열린 항목 6건의 계약 영향 여부를 판정해야 한다).
   착수 시점은 미정 — **`0.x`에 머무는 것이 지금 비용을 발생시키지 않는다.**
